## The Philosophy of Docker Swarm

In an era where container orchestration is often equated with enterprise Kubernetes clusters, **Docker Swarm** represents a conscious choice for **minimalism, simplicity, and low operational overhead**.

For small self-hosted setups, edge compute nodes, and homelabs running fewer than a few dozen services, the complexity of a full Kubernetes distribution (etcd, complex CNI plugins, API server proxies, and CRD controllers) often introduces more maintenance friction than the applications themselves require.

Docker Swarm solves this by embedding clustering directly into the Docker engine:
1. **Zero External Dependencies**: Raft consensus and cluster state are managed internally by the Docker daemon—no external etcd or datastore required.
2. **Compose-Native Specifications**: Workloads are defined using standard Docker Compose files (`docker-compose.yml`) extended with the `deploy:` stanza, eliminating the need to learn YAML-heavy Kubernetes manifests.
3. **Ultra-Low Resource Footprint**: A full Swarm manager runs comfortably on low-spec hardware (512MB–1GB RAM nodes), leaving host memory free for actual workloads.
4. **Built-in Ingress Routing Mesh**: Transparent port publishing routes incoming traffic to the appropriate container regardless of which physical node receives the request.

## Architectural Topology & Node Roles

A Docker Swarm cluster divides responsibility between two types of nodes:

| Node Role | Group Name | Responsibilities | Consensus & State |
| :--- | :--- | :--- | :--- |
| **Manager Nodes** | `docker_swarm_managers` | • Maintain cluster state<br>• Schedule tasks onto worker nodes<br>• Expose Docker Engine management API | Part of the internal Raft quorum (requires \(N/2 + 1\) majority) |
| **Worker Nodes** | `docker_swarm_nodes` | • Execute container tasks assigned by managers<br>• Report task status via internal gossip protocol | Stateless execution agents; no Raft participation |

### Sizing and Quorum Considerations
- **Single-Manager Homelab**: For a single VPS or dedicated home server, a 1-node manager cluster is rock-solid and requires zero cluster maintenance.
- **High-Availability Production**: For multi-node redundancy, maintain an **odd number of managers** (typically 3) to survive single-node loss without split-brain failure.
- **Workers**: Add worker nodes dynamically as compute demands increase without expanding the Raft management overhead.

## Networking: The Ingress Routing Mesh

Docker Swarm provides two built-in networking abstractions:

1. **Overlay Networks (VXLAN)**:
   - Encapsulates inter-container traffic between distinct physical hosts over UDP port 4789.
   - Applications communicate securely over private virtual networks using standard container names as DNS hostnames.
2. **Routing Mesh (Ingress)**:
   - When a port (e.g. 80 or 443) is published on a Swarm service, Docker opens that port across **every node in the cluster**.
   - An external request arriving at *any* node is automatically routed internally over the ingress network to a node hosting the active container.

## The 3-Tier Homelab Stack

In `infra-bootstrap-tools`, Docker Swarm is deployed as a cohesive, 3-tier foundation:

1. **Runtime & Engine**: Docker Swarm initialized declaratively across target nodes via Ansible.
2. **Perimeter & Ingress ([Caddy]({{< relref "a1.caddy.md" >}}))**: A single, modern reverse proxy that automates Let's Encrypt TLS certificates, enforces OAuth/security portal authentication, and proxies external web traffic to internal Swarm services.
3. **Cluster Operations ([Portainer]({{< relref "a2.portainer.md" >}}))**: A visual management dashboard providing real-time container logs, stack redeployments, and host health monitoring without requiring terminal access.
